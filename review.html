PROJECT / Code review

Known limits, in the open.

An independent review of the current implementation and its failure modes.

Review scope

An independent sub-agent reviewed the Go CLI, route merging, discovery, Caddy generation, directory API, Tailscale links, and tests. Other agents exercised runnable examples and captured the real UI. Collaboration used the available built-in agent messaging; Mayfly chat was not available in this environment.

The application was reviewed at commit 4868827 on September 22, 2026. The documentation work leaves core application code unchanged. Read the full review with source references and reproduction details.

Medium · Default wildcard compatibility

The generated *.test certificate is accepted by the existing Go verifier but rejected by the tested Python/OpenSSL and curl clients for app.test. Both clients explicitly trusted the generated CA; failure was hostname matching.

Workaround: configure suffix dev.test, update existing route domains and full map keys to match, and configure matching DNS or use curl --resolve. The isolated verifier uses this suffix and verifies TLS normally. Browser behavior was not established by these HTTP screenshots.

Medium · Saved and running routes can differ

CLI mutations write the registry and generated configuration before reloading Caddy. A failed reload returns an error but leaves the changed registry saved. When the admin endpoint is unavailable, automatic route updates skip reload.

Recovery: inspect the saved config, fix the reload error, and run reload. The CLI’s list command describes merged registry data, not an independently confirmed view of active routes. A future improvement would share apply-and-persist logic with the editor.

Medium · File edits appear before application

The editor merges project files on every directory request. Editing the file can therefore change visible names before the running Caddy routes change. A successful browser rename can also apply the complete currently merged set.

Workflow: run reload after changing a project map. A future UI could distinguish pending defaults from applied routes.

Low · UI tailnet flag has no effect

The CLI accepts ui --tailnet but dispatches the UI before applying the global flag. An isolated reproduction returned tailnet_enabled: false.

Workaround: enable it with reload --tailnet for a running instance, or generate --tailnet before startup, then run the UI.

What the implementation already checks

Strict request parsing, bounded bodies, Host and CSRF checks, shared file locking, and revision checks cover common editing failures. Concurrent rendering tests check that tokens and URLs remain request-specific. Real Caddy tests verify routing and reload behavior, and UI tests cover explicit reload rejection and persistence rollback.

Remaining useful work includes regression tests for these four findings, interrupted reload recovery, and remote access checks from a second tailnet device. This review is scoped engineering evidence, not a comprehensive security audit.
